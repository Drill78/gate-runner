## 4. 美术总方向

**视觉命题：一本被异教徒烧毁又缝合的中世纪远征画卷，在具有真实体积的舞台上活动起来。**

参考的取舍：

| 参考 | 提炼的设计语言 |
| --- | --- |
| DND / 中世纪 | 可辨识的职业、装备结构、冒险队伍、遗物与废墟文化；物件有用途与来历 |
| 暗黑地牢 / 漫画手绘 | 大块黑影、夸张而清楚的轮廓、粗细有变化的线条、斧凿般色块、笔触和局部排线 |
| 黑魂 / 艾尔登法环 | 庄严衰败、圣性与腐化并存、尺度对比、遗失王权；环境通过遗物和建筑讲故事 |
| 暗黑 | 厚重铁器、皮革、骨、血色仪式、地下圣所；攻击有重量，邪恶造型有物质感 |
| 克苏鲁 | 失序天象、无法闭合的环、被观测的恐惧、寄生和异质器官；按 Boss 身份集中使用 |

原创角色姓名、身份和三幕结构沿用原型。参考用于建立共同视觉语法，具体造型、徽记、服饰和怪物结构重新设计。

### 4.1 模型与材质

- 用有设计感的非写实网格表达头部、肩部、武器和异形肢体；在实际战斗镜头下仍能分辨职业与怪物。
- 手绘底色承担主要视觉信息：笔触沿体块走向，磨损集中在合理接触位置；减少全表面均匀噪点。
- 明暗采用少而明确的层次，黑影面积大但保留行动轮廓；描边按距离、轮廓和重要性变化。
- 石、铁、皮革、布、骨、腐木、湿润组织有不同的材质响应；统一渲染风格，不把所有表面做成塑料。
- 关键装备与阶段形态能从轮廓上识别，战斗中不依赖微小贴图文字。
- 立绘允许使用高质量 2D 插画，但与模型严格共享面容、头盔、服饰、武器、标志和配色。

### 4.2 三幕情绪与用色

| 幕 | 3D 场景构成 | 色彩与光 | 恐怖来源 |
| --- | --- | --- | --- |
| 荆棘边境 | 吞没道路的根系、断墙、刑架、古树圣龛、被枝条刺穿的军旗 | 冷苔绿、灰骨、暗铁；少量病态琥珀 | 自然侵占誓约与人体，森林仿佛仍在服役 |
| 月蚀回廊 | 残破修道院、悬垂祭器、碎月星盘、漆黑镜面、倒置天文构件 | 墨蓝、死紫、污银；冷月色焦点 | 异教、预言、失序天体、凝视与寄生 |
| 余烬王座 | 巨大门廊、焦黑王庭、断裂圣像、熔金裂隙、层叠灰烬与王座 | 黑曜、骨白、旧金；集中余烬红与苍白圣光 | 神圣权力的恐怖，王权、献祭与宇宙性空洞 |

禁域由黑焰、材质侵染、异常光线和空间细节共同表达。黑焰外缘和地面反光保持可读；战斗中心的危险、安全区和可交互物仍可辨认。视觉压迫感不靠把整屏压成黑色。

### 4.3 界面与演出

地图做成具有地形和建筑体积的远征沙盘，保留明确的可达连线。商店、事件、营火与选人使用同一美术体系的 3D 小场景；文字与操作界面可在屏幕层绘制。

字体、边框、图标、稀有度、血条和卡片共同使用节制的刻印与手绘语言。数值优先清楚，避免每块信息都加厚边框、发光和装饰。图标与 35 件遗物要能读出具体物件，不用临时通用图标完成最终美术验收。

Boss 入场、蓄力、出招、命中、换阶段与死亡形成完整动作叙事。镜头震动、停顿、粒子和音效有强弱层次，并提供减少动态效果的选项。双 Boss 血条与模型、目标标识对应，不覆盖头部、蓄力动作和安全路线。

详细的 3 位角色、10 位强敌、普通敌人与物件资产，见 [3D_ASSET_PLAN.md](3D_ASSET_PLAN.md)。

## 5. “真实 3D 已完成”的定义

每类实体资产至少具有可编辑的网格源文件、明确比例、材质/贴图、运行时导出文件和合理的空间边界。角色与活动怪物另有骨骼、蒙皮、完整动作与挂点；静态荆棘、门、柱、石块同样具有真实几何与体积。可共享合适的基础骨架、材质图集和模块，但各实体的最终设计能够区分。

战场采用实时 3D 相机、空间变换、遮挡、光照和阴影。美术源文件及游戏内效果都要能验证：展示模型旋转视图、线框/骨骼和运行时镜头，记录网格、材质、动画及导出情况。

临时灰盒可用于早期规则验证，状态必须标为占位。图片贴在平面上朝向相机、旧立绘模拟体积、只由球体/胶囊拼成的临时角色、单张地面背景、缺少可编辑模型文件，都不满足用户对角色与实体建模的最终要求。烟雾、火焰、魔法尾迹可以使用面片和粒子，实体的骨架与体积仍由模型承担。

## 6. 新工程的隔离与迁移

### 6.1 新目录与新仓库

由用户创建新的空文件夹和独立 Git 库，再在新目录开启新对话。不要在旧目录原地重写，也不要将旧目录递归移动进新目录。新文件夹和仓库地址以用户实际提供的值为准；名称示例 `ashen-gates-3d` 仅供参考。

新项目先记录旧基线 SHA 与标签，然后选择性迁入规则、数据和所需音频。不要复制旧 `.git`、node_modules、dist、构建缓存、环境文件、`.vercel`、`.netlify`、`.openai/hosting.json` 或临时部署凭据。旧项目的托管关联属于现有正式游戏，新项目应拥有独立的部署目标。

新项目使用独立的存档命名空间，例如 `ashen-gates-3d-*`。默认保留旧存档原样，不自动修改它；跨域导入或格式迁移如需支持，应单独设计可验证的导入流程。

### 6.2 可复用与应重建的部分

| 原文件/资源 | 用法 |
| --- | --- |

迁移时保留种子、逻辑时间、实体 ID、房间一次性结算、奖励合法性、输入锁和暂停语义。逻辑实体与渲染对象分离，让高低画质、插值、骨骼动画和相机运动不改变伤害结果。

### 6.3 技术路线建议与待定项

首发平台未确定。若延续“浏览器直接玩、键鼠与手机均可操作”的发布方式，建议默认考察 **TypeScript + Three.js + Blender + glTF/GLB**：复用纯规则与 Web 音频，重新建设 3D 渲染、动画、资源和输入层。React 可承担菜单与 HUD，逐帧战斗和变换不应依赖 React 的逐帧状态更新。

这是一条基于现有原型的工程建议。Three.js 官方明确它是 3D 库，不包含完整游戏引擎能力，因此新项目必须具体落实动画状态、场景生命周期、资源释放、存档与输入等系统。[Three.js 游戏开发说明](https://threejs.org/manual/en/game.html)

若用户更重视桌面原生版本和编辑器内的完整场景/动画工作流，可以改为评估 Godot + Blender。不要假定桌面渲染设置能直接等价导出浏览器：当前官方 Web 导出说明包含渲染方式与 C# 支持等限制，应在选型时重新核验。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

新对话只需在平台偏好确实影响选型时集中澄清首发平台。随即用一个模型、一个动画和一个材质在选定路线中完成导入验证，并写下决策理由；不要长时间维护两套平行引擎。此交接不锁定未来依赖版本。

## 7. 资产生产与运行时规范

建议新工程分为规则、呈现、界面、内容、资产源文件、运行时资产、工具和验证记录。引擎选定后调整文件夹名称，职责保持独立。

```text
docs/                     交接、艺术规范、设计决策、验收记录
src/core/                 独立规则、模拟、随机数、进度与存档
src/presentation/         场景、相机、动画、材质、灯光、特效
src/ui/                   菜单、HUD、地图交互、图鉴
content/                  职业、怪物、遗物、房间与资产关联
assets-source/            模型、雕刻、贴图、立绘的可编辑源文件
public/assets/            游戏实际加载的导出文件（Web 路线示例）
tools/                    导出、压缩、清单、预算和资源完整性检查
tests/                    规则与集成回归材料
```

每项资产记录 ID、显示名称、源文件、运行时文件、材质、骨骼、动画、尺寸、挂点、碰撞代理、LOD、来源/授权与当前状态。资产清单应能回答“这个怪物的模型在哪里、哪些动作完成了、游戏实际加载了哪个文件”。

建议保留 `.blend` 等源工程，Web 路线运行时使用 glTF/GLB。导出前统一比例与轴向，应用合适的变换，烘焙需要的纹理；导出后在目标引擎检查材质与动画。复杂 Blender 节点效果需要烘焙或在游戏中重建，不能仅凭 Blender 渲染效果认定运行时一致。[Blender glTF 导出说明](https://docs.blender.org/manual/en/4.1/addons/import_export/scene_gltf2.html)

全项目使用一套角色尺度、武器握持点、脚底原点和动画命名规则。AI 概念图与模型生成可以辅助制作；生成结果仍需完成拓扑、UV、材质、绑定、穿插修复与游戏内检验。图片生成工具的输出不等于完成模型交付。

大型源文件在新仓库建立时就决定存储方案；模型、贴图与动画应可追溯并可恢复。运行资产按需加载，正确释放纹理、网格、音频和关卡资源，避免跑完三幕后仍保留全部场景。

## 8. 相机、动作和性能

首个品质示范使用稳定的倾斜俯视镜头，让角色体积、武器姿态和场景纵深都能看见。具体角度通过真实模型决定，不照搬旧 2D 比例常量。相机、世界坐标、鼠标/触屏落点和碰撞调试视图统一校准。

地面危险区贴合实际道路，模型装饰与可伤害范围有清晰关系。荆棘逐步生长、蛛网展开、裂隙张开、火墙升起的演出，应覆盖蓄力、激活与退场阶段。伤害由模拟状态驱动，不能因某一帧动画没有播放而漏算或多算。

高兵力可能达到极大数值，不能按面板人数创建同等数量的士兵或射击对象。保持原型的数值语义，使用有上限的代表性队列、编队扩展、旗帜和强度反馈表现成长；具体显示数量由设备预算决定。

性能是品质的一部分。建议把桌面稳定 60 FPS、目标手机低画质稳定 30 FPS 作为初始设计目标，待明确设备后确定可验收的帧时间、加载与内存预算。这些是目标，不是已测结果。优先稳定帧时间、可读性和触控反馈，再提高阴影、描边、粒子和材质细节。
